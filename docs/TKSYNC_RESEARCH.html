A concrete truck
that writes code

TKSync is a React Native driver app for ready-mix concrete delivery. A driver logs the truck in, works the ticket they are hauling, fills the delivery record, collects a signature — and the app streams a GPS breadcrumb trail the entire time. The UI is the visible half. The real engineering is keeping GPS alive and publishing while Android is actively trying to put the app to sleep.

What the driver does

Two-stage login, then a single working screen with everything hung off it.

The ticket lifecycle

Eight timeline steps, each a timestamp the driver stamps or the backend fills. This is the concrete-hauling lifecycle, and it is the spine of the dashboard.

The delivery record

Five server-defined tabs, each with its own PUT endpoint and its own place in the offline queue.

TabFields
plantslump from plant / to job, temp at plant, water added + reason, truck start/end, hand added, nitrogen, fibers, load test (temp / air / slump / cylinders), notes
jobsitefull-load litres, customer water, maintenance water, super-plasticizer, conveyor, colour, fiber, washout area, load-disputed flag, notes
returnedreturned m³, disposal method (7 enum options), reason for return (7 enum options)
timeleave_plant, arrive_job, start_pour, washing, leave_job, at_plant
codpayment type, amount, wait time, notes
The entry form is fully server-driven. AdditionalEntriesModal hardcodes nothing — every field's presence, label, unit and option list comes from deliveryRecord.field_definitions[tab], served by /field-definitions. Adding a field to the driver's form is a backend change, not an app release.
And it is validated twice, on purpose. src/utils/validateDeliveryTab.ts is a line-for-line mirror of the backend's cleanTabPayload() — same field types, same enum lists. It runs before a save enters the offline queue, so a bad payload is caught at the truck instead of failing with a 422 an hour later when the driver finds signal.

The GPS system

Two independent collectors publish to one MQTT topic, and a single boolean decides which one is allowed to record. This is where the engineering went.

The 7-stage filter — written twice, in two languages

Every raw fix runs this gauntlet before it is saved or published. The TypeScript and Kotlin implementations are deliberately identical.

MQTT security — the app never sees a broker password

Idle auto-logout

A parked truck logs the driver out. The timer resets only on a saved GPS record — that is, real movement that survived all seven filters, not drift.

ElapsedEvent
0:00Any saved GPS record resets the clock and persists last_movement_time to MMKV
1:50Warning notification
2:00IDLE_AUTO_LOGOUT_EVENT → driver logout. Company session stays.

It is enforced in two places, because JS timers do not fire reliably in background: backgroundGpsTracker runs the interval in foreground, and gpsSyncManager's 30-second sync loop checks it as a backup. The timestamp is persisted so it survives an app kill.

iOS cannot detect a "While Using the App" grant. requestPermissions() checks for status === 'whenInUse' to show a Limited Tracking warning, but that branch never runs: the library's AuthorizationResult is only disabled | granted | denied | restricted, and LocationUtils.swift maps both .authorizedAlways and .authorizedWhenInUse to granted. A driver who picks "While Using the App" sees no warning, and the app runs as if it had full background permission while iOS suspends location updates on background. Detecting it needs a real read of CLLocationManager.authorizationStatus, not this return value.
The old doc is wrong about app kill. GPS_MQTT_DOCUMENTATION.md says a swiped-away app stops collecting. onTaskRemoved() deliberately does not call stopSelf() or clear tracking_active; the manifest sets stopWithTask="false" and onStartCommand returns START_STICKY and resumes from SharedPreferences on a null intent. GPS keeps collecting after a swipe. Anyone reasoning about coverage from that doc will under-count what the app records.

What to change first

  1. 01Reset firstGoodFixTime in the Kotlin service.After a run of accuracy rejections — say ten consecutive — clear it so the gate re-warms at 50 m. One line of state, and it removes the worst intermittent-gap cause.
  2. 02Give native its own MQTT token refresh timer.It already holds the API credentials and a working refreshMqttTokenViaApi(). Schedule it at TTL minus 5 minutes instead of waiting for the broker to reject the token twice.
  3. 03On iOS, restart the watcher when backgrounding while stopped.Right now stopStationaryPoll() runs and nothing replaces it, so a stationary iOS truck records nothing until the driver opens the app.
  4. 04Make a missing background-location permission loud.A persistent dashboard banner while it is missing, not one toast at login that the driver will never see again.
05

Offline-first

Concrete trucks drive through dead zones. Every mutation in the app is designed around that assumption.

Four stores, kept apart

StoreEngineHolds
tksync-authMMKVaccess / refresh tokens, company, driver, FCM token, MQTT token, lifecycle flags
tksync-gpsMMKVGPS records, trip summaries, cached ticket id
tksync-offline-queueMMKVpending saves + cached tickets, details, signing data, field definitions
tksync_native_gpsSharedPreferencesnative service records (cap 20,000 ≈ 5.5 h of driving), the js_alive flag, MQTT + API credentials
Nothing is deleted locally until the broker ACKs it. GPS storage keeps an in-memory cache with a 5-second flush timer, but addRecord and importRecord force an immediate flush anyway — the comment says it plainly: records must survive a sudden kill. A record is only marked synced inside the QoS-1 delivery callback.
06

Five ways a session ends

Each one is handled separately, and each one uploads GPS before it clears the token that recorded it.

Token refresh is single-flight

Concurrent 401s share one refreshPromise, so two requests cannot both refresh and invalidate each other — a fix for exactly the race that causes 401 storms elsewhere in this estate. On success the new access token is pushed down to the native service too, so background uploads do not go stale behind a live foreground.

Push notifications

07

Findings

Ordered by what they will cost you. Numbering matches section 10 of the companion Markdown report.

The three highest-priority items are not in this list. They are the GPS gap faults in section 04: the accuracy ratchet (E), the iOS stationary-background dead zone (F) and the background MQTT token expiry (G). Those are the ones losing real GPS data in production. Everything below is release hygiene, exposure and maintainability.
10.1

The GPS documentation has drifted from the code

correctness

GPS_MQTT_DOCUMENTATION.md is detailed and mostly right, but five claims no longer match the source. The app-kill row is the dangerous one — it states the opposite of what the code does, so anyone reasoning about coverage from the doc will under-count what the app actually records.

10.2

versionCode is still 1

ship blocker

android/app/build.gradle carries versionCode 1 / versionName "1.0" after 129 commits and four months. The first Play Store upload will succeed and the second will be rejected. Decide the versioning scheme before the first release, not after it.

10.3

The in-app log viewer ships in release builds

exposure

DebugLogViewer has no __DEV__ guard — its own docblock says “Works in release builds” — and logCapture.install() runs unconditionally at module load in App.tsx. Production builds intercept every console.log into a ring buffer and expose a floating, draggable overlay.

The API layer logs request bodies, response bodies and a truncated bearer token. That is genuinely useful for field debugging — make it a deliberate decision behind a gesture, a build flag or a support-mode toggle, rather than an accident.

10.4

Cleartext HTTP is globally permitted, and user CAs are trusted

exposure

android:usesCleartextTraffic="true" plus a network_security_config that permits cleartext for all domains and trusts user-installed CAs. User CA trust is what makes a phone trivially MITM-able with a proxy. If this was for local development against an HTTP API, scope it to a debug-only manifest and a domain allow-list.

10.5

i18n covers 3 screens out of 10

product gap

Four locales exist with 132 keys each, and useTranslation appears in exactly three files: CompanyLoginScreen, DriverLoginScreen, DashboardScreen. Everything else — Vehicle Tracking, Trip History, Notifications, Permission, every modal, all toast and alert copy, the disposal and return-reason option labels, even the native “Vehicle Tracking Active” notification — is hardcoded English.

A Quebec or Latin-American driver gets a bilingual app that reverts to English the moment they open a modal.

10.6

Test coverage is GPS-shaped only

test coverage

Five Jest files, four of them GPS. Nothing covers the offline-queue replay, token refresh, the force-logout race, or MQTT reconnect. validateDeliveryTab is pure logic with zero dependencies — it is the cheapest possible test to add and it currently has none. There is no CI to run any of them anyway.

10.7

Single author, no CI, no release pipeline

process

129 commits from one person, no .github, no lane for lint, test or build. Commit subjects are terse (“Changes”, “GPS changes”, “Fix all issues”), so the history is hard to bisect. Fine for a prototype; a liability for something about to ship to trucks.

10.8

iOS is structurally weaker than Android

platform parity

Android gets a sticky native foreground service, a boot receiver, native Paho MQTT and heartbeat self-correction. iOS gets JS watchPosition with UIBackgroundModes: location and nothing else — there is no native iOS equivalent of LocationTrackingService. Expect iOS background tracking to be less reliable, and confirm that is acceptable before promising parity.

10.9

DashboardScreen.tsx is 3,565 lines

maintainability

It holds ticket loading, the timeline, delivery-record state for five tabs, QR fetch, the plant list, twelve modal triggers, a custom scroll-wheel time picker and its own stylesheet. It is the file everyone needs to edit and nobody wants to. Pulling the modals and the delivery-record state into their own modules is the highest-leverage refactor available here.

10.10

Small things

housekeeping

A MQ → CY unit mapping is hardcoded in the dashboard with the comment “should be fixed in API”. syncManager has MAX_RETRIES = 10 but only 5 backoff delays, so the last delay silently repeats for attempts 6–10. gpsSyncManager declares BATCH_SIZE and consecutiveFailures and never uses either — leftovers from the pre-MQTT HTTP batch upload. scheduleUpload() in the Kotlin service is labelled “legacy — kept for compatibility”.

08

The other half

This app is one end of a pipeline. The rest of it lives next door.

D:\truckast\tksync\tksync-mobile-api — Express 5 on Node 18, multi-tenant (CBM, Dolese), running on pm-eks in namespace tksync. It serves the REST surface above, mints the MQTT JWTs, holds the QR encryption key, and can optionally republish HTTP-ingested GPS into the same MQTT pipeline behind REALTIME_MQTT_ENABLED.

Downstream of EMQX sits the shared realtime pipeline: gps-consumer → Redis + TimescaleDB → fleet-ws → the live dispatch map.

The QR encryption key is the customer's, not ours. It lives in ENCRYPTION_SECRET_KEY (not QR_ENCRYPTION_KEY), is 64 hex characters used as-is without hashing, and must match wherever QR tokens are produced or read — this app included. Minting a fresh one would silently invalidate every QR code the customer's readers can decode.
09

If you are picking this up

Five things that will save you a day each.

  1. 01Read the two GPS files side by side.services/backgroundGpsTracker.ts and LocationTrackingService.kt implement the same filter logic twice, in two languages. Any change to one needs the other, or foreground and background quietly disagree about what counts as movement.
  2. 02js_alive plus the 30-second heartbeat explains most of the GPS code.Once that one mechanism is clear, the lifecycle handling, the import/publish dance and half the guard flags stop looking arbitrary.
  3. 03client_id is why duplicate publishes are safe.Both collectors can and sometimes do publish the same fix. The server dedupes on that field. Do not remove it or reuse it.
  4. 04Nothing is deleted locally until the broker ACKs it.Records are marked synced inside the QoS-1 delivery callback and nowhere else. Every logout path keeps unsynced records rather than clearing them. Keep that invariant — it is the only reason offline data survives.
  5. 05validateDeliveryTab.ts mirrors the backend.If backend field types or enum lists change, this file has to change in the same PR, or offline saves start failing a day later on replay with no trace back to the cause.
